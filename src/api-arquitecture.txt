1. define customer problem
2. define where exactly the api solution should go, the scope of the solution, what it should do and not do and who uses it
3. make a first version of the api solution, simple so that it just solves the initial pain point
4. keep in mind customer context and constraints (industry, policies, existing workflows, latency)
5. if an output can affect customers, systems, buisness records, etc. identify where review or approval is required

example: Relationship managers need a faster way to prepare for client meetings using approved account context. The API solution will generate an internal structured pre-call briefing when a relationship manager opens an account record before a meeting. 
The first version will summarize approved CRM notes, recent support history, internal research, and previous meeting summaries where access is permitted. The output must remain an internal draft for relationship manager review. 
The solution will not make investment recommendations, update CRM records, send customer-facing messages, or take action without human review. Source access, permission boundaries, review requirements, and logging expectations must be validated before implementation. 

my api architecture first prompt: our sre team needs a faster way to prepare for postmortems (gathering incident information, implicated teams, incident timeline). the api solution will generate an internal structured pre-postmortem briefing when a sre opens a postmortem record.
the first version will summarise the incident, and give relevant information based on a form that must be filled out by sres before the postmortems, containing information of the incident such as why the incident happened, how it was mitigated/solved, implicated teams, incident timeline and plans for continuous improvement.
the current workflow for incident response and managment is, implicated teams of services (sres, devs, service owners, etc.) inform incident with service through teams chat, a teams call is started with copilot transcription and incident is managed in the call with the people with the tecnical context for solving the incident, sres send periodic updates to the teams chat about the incidents status. after the incident has been solved a postmortem is schedueled. key information is present in the teams chat because of the updates, however some information necessary for filling out the pre-postmortem form could be missing. we would like to obtain the necessary information of the incident using the microsoft copilot transcript information.
the solution as of now will not make recommendations for plans for continuous improvement or fill out the postmortem form. Source access, permission boundaries, review requirements, and logging expectations must be validated before implementation.
