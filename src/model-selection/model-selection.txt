Define task and capability requirements


Before you can choose a model, API capability, or solution pattern, you need to understand what the workflow actually requires. In API deployment work, this means translating a customer problem into a technical task, input/output expectation, context requirement, risk profile, and validation need.


By the end of this module, you should have the first section of your Model and Capability Selection Rationale: a clear statement of what the API must do, what constraints shape the decision, and what must be validated before recommendation or build.

Turn problem into technical task

Weak statement:

“Use AI to improve support.”

Strong statement:

“The API needs to classify short product-support messages into approved routing categories, return a priority level, and include a short audit reason for support operations.”

Define technical requirements

How many requests are expected per hour, day, or month?Are requests steady, bursty, or seasonal?How long are typical inputs and outputs?Will the workflow use retrieval, tools, or multimodal processing?What growth is expected after pilot?

Define risk and review requirements

A technically plausible selection can still be the wrong recommendation if risk and review requirements are unclear.

A strong risk and review summary might say:

“The first version can use a structured classification pattern if representative testing shows routing accuracy is acceptable, high-priority complaints reliably trigger review, structured output remains valid, and no live order data or approved-source lookup is required. If routing depends on live order status or policy interpretation, the pattern should be reconsidered.”

A strong latency and reliability note might say:“The first version should use a synchronous structured response only if testing confirms that routing output can be returned within the customer’s intake experience expectations. If peak traffic increases latency or output validity drops, the design needs fallback behavior such as review routing, queue-based async processing, or a simpler output path for routine cases.”

Safety and validation assumptions  

A more defensible recommendation might say:“Start with the shortlisted model candidate that meets the predefined routing-quality, schema, review-trigger, and latency thresholds with the strongest total task economics. Validate it against representative support messages, including seasonal peaks, ambiguous complaints, and high-priority cases. Estimate task cost using request volume, input and output length, success rate, retries, reviewer correction, and expected growth. Reserve a more capable candidate for ambiguous or high-risk cases only when the evidence shows a material benefit. Define fallback behavior for latency spikes, invalid outputs, or unavailable dependencies.”

Complete the comparison recordAlongside the rationale table, record the incumbent prompt/version, candidate model IDs, supported reasoning settings, approved inputs and tool permissions, and any compatibility changes. For each run, retain the case set, quality and review scores, latency, usage and tool costs, retries, reviewer effort, and whether evidence is observed or still planned. Link a targeted prompt change to the failure it addresses and the regression check. Name the evidence that would reverse the selection.

A concise rationale might look like this:Model Candidate B is recommended as the current baseline for the structured support-routing workflow. It met the predefined task-quality, structured-output, review-trigger, and latency thresholds and had the strongest total cost per successful task among the candidates that passed. 

Candidate A missed the required review behavior, while Candidate C did not improve successful task completion enough to justify its additional latency and cost. Revalidate the exact model IDs, supported behavior, pricing, and limits before build.
